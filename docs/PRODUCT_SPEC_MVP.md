# FastPay — полное ТЗ MVP

**Версия:** 0.1  
**Рынок первого запуска:** рестораны и кафе Киева, Украина  
**Формат:** web + PWA, без обязательной установки приложения  
**Продуктовое обещание:** «Гость оплачивает счёт за столом за 10 секунд — без терминала и ожидания официанта».

## 1. Цель и границы MVP

FastPay решает две задачи: уменьшает время между просьбой о счёте и оплатой, а владельцу даёт понятную картину QR-выручки, чаевых и работы зала. Официант ведёт открытый заказ, гость оплачивает весь счёт или выбранные позиции по уникальному QR стола.

В MVP не входят: склад, бухгалтерия, доставка, бронирования, собственный кошелёк, маркетплейс ресторанов и автоматическая интеграция с кассовыми/POS-системами. Заказы в первой версии создаются вручную официантом. Оплата обрабатывается эквайрингом самого ресторана; FastPay не хранит данные карт и не удерживает деньги.

## 2. Участники и права

| Роль | Кто это | Возможности |
|---|---|---|
| Platform admin | команда FastPay | поддержка, просмотр технических событий, блокировка аккаунта; нет доступа к платёжным секретам ресторана в открытом виде |
| Owner | владелец/управляющий | организация, филиалы, меню, столы, QR, сотрудники, настройки эквайринга, отчёты |
| Manager | администратор зала | всё по залу и заказам, сотрудники по выданному праву; без реквизитов подписки |
| Waiter | официант | PIN-вход, свой зал, создание и редактирование черновых заказов, запрос счёта, просмотр статуса платежа |
| Guest | гость | просмотр только активного счёта своего QR, выбор оплаты/чаевых/позиций, оплата, добровольное согласие на лояльность |

Доступ изолирован по `organization_id`; пользователь одного ресторана никогда не получает данные другого даже при подборе ID в URL.

## 3. Ключевые сущности

| Сущность | Главные поля | Правило |
|---|---|---|
| Organization | название, валюта UAH, часовой пояс, тариф | владеет всеми остальными данными |
| Venue | название, адрес, логотип, настройки чаевых | один ресторан может иметь несколько заведений |
| Floor / Table | зона, название, публичный UUID, QR-token, статус | QR-token невозможно угадать и можно перевыпустить |
| MenuCategory / MenuItem | название, цена, доступность, НДС/налоговая категория | цена в заказе копируется снапшотом и не меняется от редактирования меню |
| Order | table, номер, статус, waiter, итог | один стол имеет максимум один активный заказ |
| OrderItem | позиция, количество, цена-снапшот, статус оплаты | позиция может быть оплачена частично только через явную модель распределения |
| PaymentIntent | сумма, idempotency key, provider invoice ID, статус | создаётся до перехода к эквайрингу |
| PaymentAllocation | payment intent, order item, amount | фиксирует, какие позиции/доли закрывает платёж |
| Tip | сумма, тип, связанный платёж | чаевые не должны смешиваться с выручкой блюд |
| GuestProfile / Consent | телефон хешированный/защищённый, согласие, история | создаётся только после добровольного opt-in |
| AuditEvent | actor, действие, before/after, дата | неизменяемый журнал критичных действий |

## 4. Жизненный цикл заказа и стола

```text
TABLE: free → occupied → paying → paid → free
ORDER: draft → open → bill_requested → payment_pending → partially_paid → paid → closed
PAYMENT: created → provider_pending → succeeded | failed | expired | cancelled
```

- `free`: активного заказа нет.
- `occupied/open`: официант добавляет и удаляет позиции; гость видит счёт, но оплачивать может только если включена настройка «разрешить оплату до запроса счёта».
- `bill_requested`: кнопка «Позвать счёт» переводит заказ в доступный к оплате режим и опционально отправляет уведомление гостю на экране.
- `payment_pending`: существует незавершённая ссылка/инвойс. Другие платежи разрешены, но тот же набор позиций блокируется на короткий TTL (например, 10 минут), чтобы избежать двойной оплаты.
- `partially_paid`: остались неоплаченные позиции или доли.
- `paid`: сумма блюд полностью распределена по успешным платежам; закрытие заказа должно быть явным действием или автоматическим правилом ресторана.
- `closed`: заказ неизменяем, стол освобождён. Корректировки оформляются возвратом/новым заказом, а не тихим редактированием истории.

## 5. Сценарии MVP

### 5.1 Онбординг ресторана

1. Owner регистрируется по email/телефону и подтверждает контакт.
2. Создаёт организацию и первое заведение: название, адрес, часовой пояс, валюта.
3. Выбирает размер чаевых по умолчанию: 0/5/10/15% и «другая сумма».
4. Добавляет эквайринг ресторана (ключи вводятся только владельцем и хранятся зашифрованными на сервере).
5. Создаёт зоны и столы; система выпускает QR в PDF/PNG/SVG с названием ресторана, столом, короткой инструкцией и URL.
6. Добавляет сотрудников и задаёт персональные PIN-коды. PIN никогда не хранится открытым.

### 5.2 Работа официанта

1. Официант открывает PWA, выбирает заведение и вводит PIN.
2. На «Зале» видит карточки столов: свободен, занят с суммой, оплачивается, частично оплачен, оплачен.
3. Нажимает свободный стол → «Открыть заказ» → выбирает блюда, количества и комментарий к позиции.
4. При изменениях клиентская панель гостя обновляется в реальном времени.
5. Нажимает «Позвать счёт». После успешной оплаты получает не только push/in-app уведомление, но и видимый статус стола.
6. Проверяет итог, закрывает заказ и освобождает стол. Нельзя закрыть заказ при непогашенном остатке без права manager и обязательной причины.

### 5.3 Путь гостя и оплата

1. Камера считывает QR → `https://app.fastpay.ua/t/{opaque-token}`. URL не содержит последовательный ID ресторана или стола.
2. Экран показывает логотип/название, номер стола, время последнего обновления, состав текущего заказа, оплаченные и доступные позиции, итог.
3. Гость выбирает «Оплатить весь остаток» или «Разделить счёт».
4. В split-режиме выбирает целые позиции и/или сумму доли позиции (если ресторан включил деление позиций). Клиент видит только незаблокированный остаток.
5. Выбирает чаевые: нет / предустановленный процент / своя сумма. Чаевые применяются к выбранной сумме еды, а не ко всему исходному чеку.
6. Backend атомарно резервирует выбранные доли, создаёт `PaymentIntent` с idempotency key и инвойс у эквайера. Затем гость уходит на платёжную страницу провайдера.
7. Backend принимает подписанный webhook, проверяет подпись и сумму, идемпотентно меняет состояние на `succeeded`, распределяет оплату по позициям и транслирует событие всем открытым экранам.
8. Экран «Спасибо» показывает сумму, чаевые и кнопку добровольной программы лояльности. При возврате на QR отображается оставшийся счёт или подтверждение полной оплаты.

### 5.4 Split bill: обязательные правила

- Выбор позиций создаёт серверный черновик распределения; UI не является источником правды.
- Одна позиция не может быть оплачена дважды. При одновременной попытке второй гость увидит обновлённый остаток и предложение выбрать заново.
- Для количества >1 поддерживается оплата отдельных единиц (2 лимонада = две оплачиваемые единицы), без дробных копеек.
- Деление одной дорогой позиции на суммы — feature flag; при включении используется денежная точность в копейках и сумма allocation не может превышать остаток item.
- Неуспешный/просроченный инвойс снимает резерв автоматически. Успешный webhook имеет приоритет над редиректом браузера.
- Скидки и сервисный сбор в MVP либо распределяются пропорционально выбранной еде, либо отключены до реализации явной налогово-скидочной модели. Это выбирается одной политикой на заведение, не на экране гостя.

## 6. Экраны и UX

### Public guest web

1. **Статус QR:** «Стол свободен», «Заказ формируется», «Счёт готов к оплате», «Полностью оплачен». Понятный fallback без технических ошибок.
2. **Счёт:** шапка ресторана, номер стола, список с qty × ценой, оплаченные позиции отдельно, остаток, автообновление.
3. **Разделение:** чекбоксы/степперы, закреплённая нижняя панель «К оплате», предупреждение об изменении заказа другим гостем.
4. **Чаевые и подтверждение:** крупные быстрые суммы, собственная сумма с валидацией, итог «еда + чаевые».
5. **Редирект/результат оплаты:** нейтральный loading, успех, неуспех/отмена и «Попробовать снова». Нельзя сообщать успех до webhook-подтверждения.
6. **Лояльность:** отдельное добровольное согласие с ссылками на политику; отказ не ухудшает оплату.

### Staff PWA

1. PIN login и выбор смены/заведения.
2. Зал: адаптивная сетка столов, фильтр по зоне и легенда статусов. Цвет не единственный носитель смысла.
3. Карточка заказа: меню с категориями и поиском, корзина, изменение количества, комментарии, сумма, история платежей, «Позвать счёт».
4. Уведомления: оплата начата / частичная / успешная / неуспешная, с прямой ссылкой на стол.
5. Offline UX: заранее объяснить, что данные не синхронизируются; блокировать опасную отправку, когда сети нет.

### Owner dashboard

1. Сегодня: QR-выручка, доля QR-оплат, средний чек, чаевые, число закрытых столов.
2. Период и фильтр заведения.
3. Популярные блюда, продажи и чаевые по официантам, время «заказ → оплата» и «запрос счёта → оплата».
4. Настройки: заведения, зоны/столы/QR, меню, сотрудники/PIN, чаевые, эквайринг, брендирование.

## 7. Бизнес-правила и расчёты

- Все деньги хранятся целым числом в минимальной денежной единице (`amount_kopecks`); форматирование UAH — только на границе UI.
- `order_total = сумма item.unit_price_snapshot × quantity − discounts + service_fee`.
- `outstanding_food = order_total − успешные allocations еды`; `paid_tip` считается независимо.
- В отчёт QR-выручки входят только успешные платежи, относящиеся к еде; отмены и возвраты показываются отдельной метрикой.
- Сумма платежа у провайдера всегда сравнивается с суммой PaymentIntent; расхождение переводится в ручную проверку.
- Изменение цены блюда влияет только на будущие позиции. Удаление позиции из меню не уничтожает историю.
- Возврат создаёт отдельную запись и обратное распределение; не редактирует успешную оплату.
- Один открытый заказ на стол; перенос заказа между столами — действие manager с аудитом.

## 8. Уведомления и real-time

Базовый транспорт — WebSocket/SSE с авторизацией для staff и одноразовым публичным токеном/каналом для guest. Критичные события также фиксируются в БД. MVP поддерживает in-app уведомления; browser push и Telegram/Slack — следующий этап.

События: `order.updated`, `bill.requested`, `payment.pending`, `payment.succeeded`, `payment.failed`, `payment.expired`, `table.status_changed`.

## 9. Нефункциональные требования

- Mobile-first; guest flow работает в Safari iOS и Chrome Android последних двух основных версий.
- Время первой интерактивной загрузки guest-счёта: целевой p75 ≤ 2.5 сек на 4G; UI устойчив к медленному интернету.
- API p95 для чтения активного счёта ≤ 500 мс без вызова эквайера.
- Доступность: семантическая разметка, контраст WCAG AA, клавиатурная навигация в панели персонала.
- Наблюдаемость: структурированные логи, request ID, ошибки фронта/бэка, алерты по webhook failures.
- Резервное копирование БД, восстановление проверяется до пилота.

## 10. Безопасность, приватность и платежи

- Только HTTPS, HSTS, безопасные cookies, CSRF-защита для cookie-сессий, rate limiting для публичного QR и PIN.
- Пароли/PIN хешируются современным password hash; секреты эквайринга зашифрованы at rest и отсутствуют в логах/клиенте.
- Webhook: проверка подписи, allowlist при поддержке провайдера, idempotency по event ID, журнал сырых метаданных без секретов.
- QR — capability URL, поэтому токен длинный и криптографически случайный; владелец может перевыпустить QR при утрате наклейки.
- Телефон для лояльности запрашивается после оплаты с отдельным информированным согласием. Нужны политика конфиденциальности, срок хранения и механизм удаления данных.
- Перед запуском в Украине требуется отдельная юридическая и фискальная проверка: договорная схема с эквайером, РРО/ПРРО, чеки, персональные данные и правила возвратов. Это не заменяется настоящим ТЗ.

## 11. Метрики успеха MVP

- ≥ 50% закрытых чеков пилотного ресторана оплачиваются через QR через 30 дней после внедрения.
- Медиана «запрос счёта → успешная оплата» ≤ 3 минут.
- Доля успешно завершённых платёжных попыток ≥ 95% (исключая отмены гостем).
- 0 двойных списаний и 0 случаев двойного закрытия позиции.
- Owner может самостоятельно создать стол и распечатать QR менее чем за 5 минут.

## 12. Явные решения до начала разработки

1. Первый эквайер и точный сценарий его invoice/webhook API.
2. Нужен ли split одной позиции в MVP или достаточно целых позиций/единиц количества.
3. Политика скидок, сервиса и фискального чека на старте.
4. Языки первого релиза (рекомендуется UK + EN; RU — отдельное бизнес-решение).
5. Кто оплачивает комиссию эквайринга и на каком счёте отображаются чаевые.
