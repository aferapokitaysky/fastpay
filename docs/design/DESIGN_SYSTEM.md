# Дизайн-система FastPay

Источник UX-требований — `docs/PRODUCT_SPEC_MVP.md` (раздел 6 «Экраны и UX», раздел 9 НФТ). Этот документ фиксирует токены и компоненты, чтобы Codex (`apps/web`) не изобретал их заново по ходу разработки. Это отправная точка, не финальный аудит — обновлять по мере появления реальных экранов.

## 0. Принципы

1. **Гостевой экран — приоритет №1.** Он открывается один раз незнакомым человеком на его собственном телефоне (часто старом, часто на плохой сети) — минимум когнитивной нагрузки, крупные тач-таргеты, ничего не грузится дольше 2.5 сек на 4G (НФТ, §9).
2. **Деньги никогда не выглядят двусмысленно.** Одна типографская трактовка суммы во всех экранах — см. токен `Money` ниже. Форматирование — только через `formatMoney()` из `apps/web/lib/money.ts`, нигде не форматировать сумму по месту.

   > **Почему не `style: 'currency'`.** Первая редакция этого документа предписывала `Intl.NumberFormat('uk-UA', { style: 'currency', currency: 'UAH' })`. Это оказалось ошибкой: символ гривны зависит от версии ICU, поэтому Node на SSR отдавал `320,00 ₴`, а Chromium на клиенте — `320,00 грн`. React падал с hydration mismatch на каждой сумме, а гость видел разные обозначения валюты. Правило заменено: форматируем **только число** (`minimumFractionDigits: 2`, стабильно между средами) и добавляем `₴` сами.
3. **Статус — не только цвет.** Слепота на цвет и яркое солнце на телефоне гостя — обычное дело; статус стола/заказа всегда дублируется иконкой/текстом (см. `docs/PRODUCT_SPEC_MVP.md` §109, «Staff PWA»).
4. **Кириллица — родной язык интерфейса**, UK первично, EN — сразу закладывается в токены (не патчится потом); RU — отдельное бизнес-решение (см. ТЗ §12.4), в токенах не блокируем, но по умолчанию не включаем.

## 1. Токены

### Цвет

| Токен | Значение (light) | Назначение |
|---|---|---|
| `color.brand.primary` | `#0F6B4C` (глубокий зелёный) | Основные действия: «Оплатити», «Позвати рахунок» |
| `color.brand.primary.hover` | `#0B5A3F` | hover/active состояние primary |
| `color.neutral.bg` | `#FAFAF8` | фон страниц |
| `color.neutral.surface` | `#FFFFFF` | карточки, sticky-панели |
| `color.neutral.border` | `#E4E4E0` | разделители, обводки |
| `color.neutral.text` | `#1A1A18` | основной текст |
| `color.neutral.text.muted` | `#6B6B66` | подписи, второстепенный текст |
| `color.status.free` | `#3AA65A` | стол свободен |
| `color.status.occupied` | `#E0913A` | стол занят / есть открытый заказ |
| `color.status.paying` | `#3B7FD9` | идёт оплата |
| `color.status.paid` | `#6B6B66` | оплачено / закрыт |
| `color.status.attention` | `#D0413A` | требует внимания / ошибка платежа |
| `color.tip.accent` | `#C98A2C` | выбранный вариант чаевых, некритичный акцент |

Каждый `color.status.*` обязан иметь парную иконку (кружок/точка + текст статуса), не полагаться только на цвет — см. Принцип 3.

Тёмная тема — не в MVP; токены выше называть с расчётом на будущий `@media (prefers-color-scheme: dark)`-слой, но не реализовывать сейчас (не строить то, что не нужно уровню MVP).

### Типографика

| Токен | Значение | Назначение |
|---|---|---|
| `font.family.base` | системный стек: `-apple-system, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif` | весь UI — системный шрифт кириллицу рендерит быстро и без FOUT на слабой сети гостя |
| `font.size.money.lg` | 28px / 700 | итоговая сумма к оплате на гостевом экране |
| `font.size.money.md` | 18px / 600 | суммы позиций, суммы в панели официанта |
| `font.size.body` | 16px / 400 | базовый текст (не меньше — гость держит телефон в руке, часто на солнце) |
| `font.size.caption` | 13px / 400 | подписи, таймстемпы («оновлено 2 хв тому») |

### Spacing / Radius / Shadow

| Токен | Значение |
|---|---|
| `space.*` | шкала 4/8/12/16/24/32/48px |
| `radius.control` | 12px (кнопки, инпуты) |
| `radius.card` | 16px (карточки стола, карточка позиции) |
| `shadow.sticky` | `0 -4px 12px rgba(0,0,0,0.08)` — для закреплённой нижней панели «До оплати» |

### Motion

| Токен | Значение | Назначение |
|---|---|---|
| `motion.duration.fast` | 120ms | нажатия, чекбоксы split bill |
| `motion.duration.base` | 200ms | появление/исчезновение уведомлений, обновление суммы |
| `motion.easing.standard` | `cubic-bezier(0.2, 0, 0, 1)` | все переходы |

Обновление суммы после события `order.updated` (см. `docs/architecture/DOMAIN_AND_ARCHITECTURE.md`) анимируется, а не дёргается мгновенно — гость должен заметить, что счёт изменился, а не только увидеть новое число.

## 2. Компоненты (ключевые для MVP)

### `Money`
- **Назначение:** единственная точка форматирования суммы в приложении.
- **Props:** `amountKopecks: number`, `size: 'lg' | 'md'`.
- **Правило:** компонент, а не утилита форматирования, вызываемая из разметки — чтобы шрифт/трекинг суммы нельзя было случайно разъехаться между экранами.

### `TableStatusCard` (панель официанта, экран «Зал»)
- **Варианты:** `free`, `occupied`, `paying`, `paid`, `attention` — маппятся на `color.status.*`.
- **Состав:** номер стола, статус-иконка+текст, сумма (если есть открытый заказ), время последнего изменения.
- **Доступность:** статус объявляется screen reader'ом текстом, не только цветом/иконкой.

### `BillItemRow` (гостевой счёт и панель официанта)
- **Состав:** название позиции, `qty × unitPrice`, итог по позиции, статус оплаты позиции (для split bill — см. ниже).
- **Вариант split:** чекбокс/степпер слева, задизейблен если позиция зарезервирована другим гостем (`payment_pending` — см. ТЗ §5.4).

### `SplitSelector`
- Список `BillItemRow` в режиме выбора + закреплённая снизу панель `BillSummaryBar` с текущей выбранной суммой и кнопкой «Продовжити».
- Явно показывает предупреждение, если состав счёта изменился, пока гость выбирал (конкурентная оплата — ТЗ §5.4).

### `TipSelector`
- Быстрые проценты (кнопки-чипы, значения берутся из настроек заведения, не хардкодятся) + опция «своя сума» с валидацией мин/макс.
- Явно показывает, к какой сумме применяется процент (еда без учёта чаевых — ТЗ §5.3, шаг 5), а не общая цифра — частая точка путаницы у гостя.

### `BillSummaryBar`
- Sticky-панель внизу экрана (`shadow.sticky`), всегда видна без скролла: сумма к оплате + основная кнопка действия.
- Никогда не перекрывает системную навигацию iOS/Android (safe-area insets обязательны — гостевой флоу почти всегда в браузере на телефоне).

### `LiveStatusBanner`
- Ненавязчивое «Рахунок оновився» при получении realtime-события, не модальное окно — не прерывать гостя, который уже читает счёт.

### `OwnerKpiTile` (дашборд владельца)
- Число + подпись + опциональная дельта к предыдущему периоду.
- Состав KPI берётся из ТЗ §6 «Owner dashboard»: сегодня — QR-выручка, доля QR-оплат, средний чек, чаевые, число закрытых столов.

## 3. Ключевые паттерны (потоки экранов)

### Гостевой поток (`apps/web`, публичный, без авторизации)
`no_active_order` → `ready_to_pay` (весь счёт / split) → `TipSelector` → редирект к эквайеру → нейтральный loading → `fully_paid`/ошибка. Все состояния явно перечислены в `docs/IMPLEMENTATION_PLANS.md` (План A1) — дизайн обязан покрыть каждое, включая `qr_invalid` и `temporarily_unavailable`, а не только happy path.

### Поток официанта (Staff PWA)
PIN-вход → «Зал» (`TableStatusCard` grid, фильтр по зоне) → карточка заказа (меню, `BillItemRow` в режиме редактирования, «Позвати рахунок») → realtime-уведомление об оплате с deep link обратно на стол.

### Поток владельца
Дашборд (`OwnerKpiTile` grid) → настройки (заведения/зоны/столы/QR/меню/сотрудники/чаевые/эквайринг) — все деструктивные действия (удаление стола, отзыв QR) через подтверждение, без исключений.

## 4. Доступность и адаптивность

- Минимальная ширина вьюпорта — 320px (ТЗ §6, «Public guest web»), контраст текста — WCAG AA.
- Тач-таргеты не меньше 44×44px на гостевом экране (телефон в руке, часто на ходу).
- Панель официанта должна работать с клавиатурной навигацией (НФТ §9) — не только тач.
- Локаль по умолчанию — `uk-UA`; все даты/время через `Intl.DateTimeFormat`, не ручное форматирование.

## 5. Что сознательно не входит в MVP

Тёмная тема, кастомизация брендинга сверх логотипа/названия/акцентного цвета заведения, анимированные иллюстрации/иконки за пределами статусов — всё это не блокирует запуск и добавляется отдельным ADR/итерацией, а не «раз уж мы тут».
