# Асинхронная коммуникация Codex ↔ Claude

Эта папка заменяет «сообщения в голове»: любое решение, блокер или handoff остаётся рядом с кодом и попадает в PR. Это не место для ключей, персональных данных, токенов, платёжных payloads или секретов.

## Файлы

| Файл | Для чего | Кто пишет |
|---|---|---|
| `INBOX.md` | очередь коротких задач и запросов между агентами | оба |
| `DECISIONS.md` | принятые архитектурные/API решения (ADR-lite) | оба |
| `HANDOFF.md` | что изменено в текущей ветке, как проверить, риски | автор feature |
| `inbox/` | большие предложения/контракты, по одному файлу на тему | оба |

## Протокол

1. Перед началом прочитать `INBOX.md`, `DECISIONS.md`, актуальный API contract и `git status`.
2. Создать ветку `feat/<area>-<short-name>` от свежего `main`.
3. Если работа затрагивает общий контракт, сначала добавить запрос в `INBOX.md` со статусом `OPEN`; не реализовывать предположение как факт.
4. Получатель переводит запись в `ACKNOWLEDGED`, отвечает прямо под ней и при необходимости создаёт ADR в `DECISIONS.md`.
5. Перед коммитом автор обновляет `HANDOFF.md`: изменения, команды проверки, API impact, rollback/risks.
6. В PR обязательно ссылаться на ID сообщения (`COM-###`) и ADR (`ADR-###`). После merge закрыть запись, но не удалять историю.

## Формат сообщения

```md
### COM-001 — короткий заголовок
- From: Codex | Claude
- To: Codex | Claude | both
- Status: OPEN | ACKNOWLEDGED | RESOLVED | BLOCKED
- Branch/PR: `feat/...` / #123
- Context: что произошло и почему важно.
- Request/decision needed: один конкретный вопрос или предложение.
- Acceptance: как понять, что ответ достаточен.
- Reply: ответ получателя, дата и ссылка на commit/ADR.
```

## Конфликты владения

- Claude владеет `apps/api`, миграциями, payment adapter и OpenAPI generation.
- Codex владеет `apps/web`, `packages/ui`, PWA и e2e.
- `packages/contracts`, `.github`, root config и `docs/api` — shared. В shared-файлах один агент делает change, второй проверяет через PR; не переписывать параллельно.
- При расхождении приоритет: безопасность платежей → целостность данных → контракт API → UX → скорость реализации.
